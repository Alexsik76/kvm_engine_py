# UART-протокол: kvm_engine_py ↔ RP2040-Zero (front_panel)

**Версія документа:** 1.0
**Версія протоколу:** 1
**Статус:** контракт між Python-стороною (`kvm_engine_py/app/hardware/front_panel.py`) і прошивкою RP2040-Zero (`kvm_engine_py/firmware/`).

---

## 1. Призначення

Документ фіксує формат обміну даними між Raspberry Pi 4 (далі — Pi) і платою RP2040-Zero (далі — плата) для функції віддаленого керування front-panel роз'ємом цільового PC: натискання кнопок Power/Reset, отримання стану індикаторів PWR_LED і HDD_LED.

Front-panel модуль є **опціональною** частиною KVM-системи. Pi працює з повною функціональністю (відео, HID) і без плати; за відсутності плати функції цього протоколу просто не активуються.

## 2. Фізичний рівень

| Параметр | Значення |
|---|---|
| Інтерфейс | UART |
| Швидкість | 115200 бод |
| Формат кадру | 8N1 (8 біт даних, без паритету, 1 стоп-біт) |
| Контроль потоку | відсутній |
| Лінії Pi 4 | TXD = GPIO14, RXD = GPIO15 (UART0) |
| Лінії RP2040 | визначаються прошивкою; за замовчуванням GP0=SDA, GP1=SCL зі схеми перевизначаються на UART (GP0=TX, GP1=RX) — **примітка:** схема показує I²C-pinout, але фактично використовується UART; провідне з'єднання те саме |
| Довжина кабелю | до 1 м |
| Рівні | 3.3 В TTL з обох сторін |
| GND | спільний з живленням плати від Pi (5V лінія) |

## 3. Формат фрейма

Кожен фрейм — це JSON-об'єкт у вигляді одного рядка тексту, завершеного символом `\n` (LF, 0x0A).

Кодування: UTF-8 (на практиці використовуються лише ASCII-символи).

Імена полів: **snake_case**.

Максимальна довжина одного фрейма: **256 байт** (включно з символом завершення). Перевищення — підстава відкинути фрейм без обробки.

Приклад правильного фрейма:

```
{"type":"led_status","pwr":"on","hdd":"idle"}\n
```

Кожен фрейм — самодостатній. Часткові фрейми, мульти-лайн JSON, додаткові пробіли всередині не дозволені.

## 4. Послідовність встановлення зв'язку

Pi виступає **активною** стороною: ініціює зв'язок, перевіряє наявність плати. Плата — **реактивна**: лише відповідає на команди.

### Probe-послідовність при старті

При старті `kvm_engine_py`:

1. Відкриває послідовний порт.
2. Виконує до **5 спроб** надіслати `{"type":"ping"}\n` з очікуванням відповіді типу `pong`.
3. Інтервали між спробами: **200 мс, 400 мс, 800 мс, 1600 мс, 3000 мс** (експоненційне зростання).
4. Таймаут очікування `pong` на кожну спробу: **500 мс**.
5. Якщо отримано валідний `pong` — підсистема активується, виставляється capability `front_panel: true`, реєструється WS-маршрут `/ws/front_panel`.
6. Якщо всі 5 спроб невдалі — підсистема залишається неактивною, capability `front_panel: false`, у лог пишеться `WARN: front-panel module not detected, feature disabled`. Подальші автоматичні спроби не виконуються.

### Поведінка плати при boot

Плата при старті:
1. Виставляє виходи PWR_BTN/RST_BTN у безпечний стан (low, оптопари вимкнено).
2. Починає семплювати входи PWR_LED/HDD_LED.
3. Слухає UART, чекає команд.
4. **Самостійно нічого не надсилає до моменту першого `ping`.**

Після успішної відповіді на `ping` плата починає періодично надсилати фрейми `led_status` (раз на 100 мс).

## 5. Команди від Pi до плати

| `type` | Опис | Параметри |
|---|---|---|
| `ping` | Перевірка наявності плати | — |
| `power_press` | Короткий імпульс на PWR_BTN (стандартне натискання) | — |
| `power_hold` | Довгий імпульс на PWR_BTN (force off) | — |
| `reset` | Імпульс на RST_BTN | — |

Тривалість імпульсів задана у прошивці, не у протоколі:
- `power_press`: **100 мс**
- `power_hold`: **6000 мс**
- `reset`: **100 мс**

Приклади:

```
{"type":"ping"}
{"type":"power_press"}
{"type":"power_hold"}
{"type":"reset"}
```

## 6. Відповіді від плати до Pi

### 6.1. `pong` — відповідь на `ping`

```json
{"type":"pong","fw_version":"1.0","protocol":1}
```

| Поле | Тип | Опис |
|---|---|---|
| `fw_version` | string | Версія прошивки у форматі `"major.minor"` |
| `protocol` | int | Версія протоколу (поточна — 1) |

### 6.2. `ack` — підтвердження виконання команди

Надсилається у відповідь на `power_press`, `power_hold`, `reset` **після завершення** імпульсу.

```json
{"type":"ack","cmd":"power_press"}
```

| Поле | Тип | Опис |
|---|---|---|
| `cmd` | string | Назва команди, яка була підтверджена |

Pi не блокується, очікуючи `ack` — вона лише фіксує, що команда виконана. Якщо `ack` не приходить за 10 секунд після `power_hold` (найдовшої команди + запас) — це не критична помилка, але пишеться у лог.

### 6.3. `led_status` — періодичний стан індикаторів

Плата надсилає цей фрейм **раз на 100 мс** після успішного `ping`.

```json
{"type":"led_status","pwr":"on","hdd":"idle"}
```

| Поле | Можливі значення | Опис |
|---|---|---|
| `pwr` | `"unknown"` \| `"off"` \| `"on"` \| `"blinking"` | Стан індикатора PWR_LED |
| `hdd` | `"unknown"` \| `"idle"` \| `"active"` | Стан індикатора HDD_LED |

#### Семантика класифікації

Плата веде ковзне вікно семплів довжиною **1500 мс**. Класифікація:

**PWR:**
- `off` — за останні 1500 мс рівень стабільно low
- `on` — за останні 1500 мс рівень стабільно high
- `blinking` — за останні 1500 мс було ≥ 2 переключень рівня
- `unknown` — вікно ще не наповнене (перші 1500 мс після старту), або внутрішня помилка читання

**HDD:**
- `idle` — за останні 1500 мс жодних переключень
- `active` — за останні 1500 мс було ≥ 1 переключення
- `unknown` — вікно ще не наповнене, або внутрішня помилка

Стан `unknown` може повертатись не лише при cold start. Це універсальне значення "стан невідомий", клієнт повинен трактувати його однаково в усіх випадках.

### 6.4. `error` — помилка обробки

Надсилається, якщо плата отримала фрейм, який не вдалось обробити.

```json
{"type":"error","reason":"unknown_command","received":"foo_bar"}
```

| Поле | Тип | Опис |
|---|---|---|
| `reason` | string | Код помилки: `unknown_command`, `malformed_json`, `frame_too_long` |
| `received` | string | (необов'язкове) фрагмент проблемного фрейма для діагностики |

## 7. Поведінка при помилках

### На стороні плати

- **Нерозпізнаний тип команди** → відправити `error` з `reason: "unknown_command"`, продовжити роботу.
- **Невалідний JSON** → відправити `error` з `reason: "malformed_json"`, продовжити роботу.
- **Фрейм > 256 байт** → відкинути без обробки, відправити `error` з `reason: "frame_too_long"`.
- **Внутрішня помилка GPIO/таймера** → виставити відповідне поле в `led_status` у `unknown`, продовжити роботу. Не зупинятись.

Плата ніколи не входить в нерозпізнаний стан. Будь-яка помилка — recoverable.

### На стороні Pi

- **Невалідний JSON у відповіді плати** → залогувати, відкинути фрейм, продовжити.
- **Таймаут очікування `pong` під час probe** → перейти до наступної спроби (див. розділ 4).
- **Раптове закриття порту під час роботи** → залогувати `ERROR`, виставити `front_panel` у деградований стан, повідомити підключені WS-клієнти. Не намагатись автоматично перепідключитись (див. розділ 9).

## 8. Версіонування

Поле `protocol` у `pong` дозволяє Pi перевірити сумісність із прошивкою.

- Якщо `protocol` від плати **дорівнює** очікуваному Pi — підсистема активується нормально.
- Якщо `protocol` **відрізняється** — Pi пише `WARN: front-panel protocol mismatch (board=X, expected=Y)`, але не блокує роботу. Сумісні команди обробляються, несумісні логуються.

Збільшення мажорної версії протоколу зарезервоване для несумісних змін; на момент v1 — таких немає.

## 9. Future considerations (не реалізовано в v1)

- **Manual re-initialization з UI.** При втраті зв'язку з платою під час роботи Pi (наприклад, фізичне переключення кабелю) — наразі потрібен рестарт `kvm_engine_py`. У майбутньому планується додати кнопку "Re-detect front-panel module" в налаштуваннях клієнта, яка викличе повторну probe-послідовність без рестарту сервісу.
- **Налаштування тривалості імпульсів через протокол.** Зараз тривалості зашиті в прошивку. Якщо різні материнки виявлять чутливість до різних тривалостей — додати команди типу `set_pulse_duration`.
- **Підписка/відписка на `led_status`-стрім.** Зараз стрім завжди активний після `ping`. У разі необхідності економії UART-смуги — додати `subscribe`/`unsubscribe`.
