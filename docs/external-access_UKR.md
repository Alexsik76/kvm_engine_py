# Зовнішній доступ до пристрою — пропозиція

> Це **пропозиція**, а не єдиний правильний спосіб. У локальній мережі пристрій повністю
> працездатний без жодного з варіантів нижче — зовнішній доступ лише додається зверху.
> Організація може обрати й власний метод (внутрішня VPN, відкриття порту на своєму шлюзі
> тощо); архітектура пристрою цьому не заважає.

## Як це влаштовано всередині

Пристрій працює за принципом **єдиного походження** (single-origin): веб-інтерфейс, API і
канали WebSocket (керування, передня панель) віддаються з однієї адреси через локальний
проксі (Caddy на порту 80). Сторінка звертається до сервера **відносними** адресами, тому
той самий застосунок працює за будь-якою адресою, з якої його відкрили — локальний IP,
імʼя в мережі, VPN-адреса чи публічний домен — і його не треба перезбирати.

Важливо розрізняти два види трафіку:

1. **Керування** — це HTTP(S) і WebSocket: вхід, перелік вузла, узгодження WebRTC, клавіатура
   й миша, передня панель.
2. **Відео** — це потік WebRTC поверх **UDP**, який іде **напряму** між браузером і пристроєм
   (порт 30000), а не через канал керування.

Будь-який спосіб зовнішнього доступу має пропустити **обидва** види трафіку. Якщо пройде лише
керування, інтерфейс відкриється, але відео не зʼявиться — саме на цьому й зупиняється
частина рішень (див. розділ про Cloudflare).

## Навіщо ззовні потрібен HTTPS

У локальній мережі вистачає звичайного HTTP. Але деякі можливості браузера працюють **лише в
захищеному зʼєднанні (HTTPS)**. Передусім це Keyboard Lock — механізм, що дозволяє в
повноекранному режимі перехоплювати службові клавіші (`Esc`, `Tab`, `Alt`, `Meta`) і
передавати їх на цільовий ПК (наприклад, `Esc` для виходу з BIOS). Без HTTPS браузер
перехоплює ці клавіші сам, і `Esc` лише виходить з повноекранного режиму. Тому зовнішній шар
бажано налаштувати так, щоб він давав HTTPS — обидва варіанти нижче це вміють.

## Варіант A — Tailscale (рекомендований; перевірений)

Tailscale — це приватна мережа на основі WireGuard з власним механізмом узгодження зʼєднань.
Усі пристрої входять до однієї спільної мережі, прив'язаної до облікового запису. Для
подарованого пристрою цей обліковий запис має належати організації, а не приватній особі.

Чому варіант добре підходить для цього пристрою:

- Пропускає і керування, і відео-UDP **без додаткових налаштувань** — це повноцінна приватна
  мережа рівня IP, тож пряме зʼєднання для відео встановлюється само собою, без TURN і без
  відкриття портів на роутері.
- Самостійно встановлює зʼєднання навіть тоді, коли обидва боки за NAT (на крайній випадок
  трафік іде через проміжні вузли Tailscale), тому публічна IP-адреса не потрібна.
- Дає справжній HTTPS на адресі виду `https://<імʼя>.<мережа>.ts.net` без ручної роботи з
  сертифікатами.

Орієнтовні кроки на пристрої:

1. Встановити клієнт: `curl -fsSL https://tailscale.com/install.sh | sh`
2. Підключити пристрій до мережі організації: `sudo tailscale up`
3. Увімкнути сертифікати HTTPS для цієї мережі в адмін-консолі Tailscale (розділ DNS →
   MagicDNS → HTTPS Certificates).
4. Відкрити локальний веб (Caddy на порту 80) назовні по HTTPS:
   `sudo tailscale serve --bg http://localhost:80`
5. Відкрити адресу `https://<імʼя>.<мережа>.ts.net` з будь-якого пристрою, де теж встановлено
   Tailscale.

Хто має доступ, визначають правила доступу всередині мережі. Обмеження: на кожному пристрої,
що підключається ззовні, теж має стояти клієнт Tailscale. Для робочих компʼютерів це
прийнятно; для сценарію «відкрив будь-який браузер де завгодно, нічого не встановлюючи» — ні.

## Варіант B — Cloudflare Tunnel (плюс окреме рішення для відео)

Cloudflare Tunnel (`cloudflared`) встановлює зʼєднання від пристрою до мережі Cloudflare й
публікує веб на власному домені (`https://kvm.example.org`) без публічної IP-адреси та без
відкриття портів на роутері. Сертифікат HTTPS видає й оновлює сам Cloudflare. Для сценарію
«відкрив будь-який браузер де завгодно, без VPN-клієнта» це зручніше за Tailscale.

Орієнтовні кроки: завести (безкоштовний) обліковий запис Cloudflare на власний домен →
встановити `cloudflared` на пристрій → створити тунель і спрямувати його на локальний Caddy
(`http://localhost:80`).

### Чому самого тунелю Cloudflare для відео замало

Тунель Cloudflare передає веб-трафік (HTTP/HTTPS) і окремо може передавати зʼєднання SSH/RDP.
Він проведе все керування — вхід, узгодження зʼєднання, клавіатуру й мишу, — і інтерфейс
відкриється нормально. Але відео — це потік WebRTC поверх UDP, а UDP через веб-тунель
Cloudflare не передається: щоб отримати відео, браузеру потрібне пряме UDP-зʼєднання з
пристроєм, якого тунель не створює. Через «голий» тунель ви побачите робочий інтерфейс і
**чорний відеоплеєр**. Щоб відео запрацювало, потрібен один із двох додаткових кроків: або
(1) є власна публічна IP-адреса й на роутері відкривається UDP-порт 30000 на пристрій — тоді
відео йде напряму, повз тунель; або (2) піднімається сервер TURN, який ретранслює відео-UDP
(власний `coturn` на публічному вузлі чи готовий сервіс, наприклад Cloudflare Realtime).
Tailscale цих кроків не потребує, бо передає UDP сам.

## Коротке порівняння

| | Tailscale (A) | Cloudflare Tunnel (B) |
|---|---|---|
| Керування (HTTP/WS) | так | так |
| Відео (UDP) без зайвих налаштувань | **так** | **ні** — потрібен відкритий порт або TURN |
| Власна публічна IP-адреса | не потрібна | не потрібна (для тунелю) / потрібна (для відкриття порту) |
| HTTPS | через `tailscale serve` | автоматично від Cloudflare |
| Клієнт на пристрої користувача | потрібен | не потрібен (звичайний браузер) |

Підсумок: для доступу з невеликого кола відомих компʼютерів простіший і повніший —
**Tailscale**; для «будь-який браузер, будь-де» — **Cloudflare**, але обовʼязково з окремим
рішенням для відео (відкритий UDP-порт або TURN).
